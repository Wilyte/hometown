# 地图编辑器方案（v6 · Campground & Lake）

> 状态：方案，未实施 ｜ 2026-11-08 ｜ 对应需求：「规划下如何做一个地图编辑器，能实现哪些编辑效果，给方案」
>
> 本文只回答“怎么做、能做到什么程度、先做什么”。所有数字都来自当前仓库代码与已有实测记录；
> 与 Web 构建相关的内容以并行的 Web 环境改动（PR #1）为前提，合入后即成立。

## 0. 一句话结论

**在现有 Godot 编辑器上增量做，不另起一套 Web 编辑器。** 先补齐属性面板、多选、重做、贴地放置和可靠的保存链路，
再把同一套场景通过 URL 暴露到浏览器（`editor.tscn` 其实已经打进 Web 包了）。
真正的工作量不在 3D 拖动，而在**地图数据与构建包的解耦**：让 `map.json` 在运行时加载、在浏览器里直接存回项目目录，
否则每改一棵树都要重新导出约 60 MB 的 Web 包，编辑器就没法日常用。

## 1. 现状盘点

### 1.1 已经有的

| 能力 | 现状 | 位置 |
|---|---|---|
| 地图数据 | `map.json` v1：`items[]` 每项含 `part / pos / rot_deg / scale`；当前 174 条、62 个基础类别、174 个变体（这套 kit 的每个摆放件都是独立网格） | `v6/data/maps/campground.json`、`v6/scripts/map_world.gd` |
| 拼装/观看器 | 相机、背景渐变、半球光/主光/轮廓光、接触阴影烘焙、地形高度图、4 个程序化角色、桌面/触摸手势 | `v6/scripts/main.gd` |
| 编辑器 | 选中（AABB 射线）、地面拖动（4 m 吸附）、Shift 上下（0.25 m）、Y 轴旋转（15°/1°）、等比缩放（±10%）、刷子放置、变体切换、复制、删除、撤销（60 步 JSON 快照）、存盘、网格、取景、重烘阴影 | `v6/scripts/editor.gd`（615 行） |
| 自检 | `--edit-selftest`：放一件 → 存盘 → 重读 → 比对条数与坐标；文档记录为 PASS | `v6/scripts/editor.gd` |
| Web 构建 | Godot 4.7 / `gl_compatibility` / 静态导出；原始首屏约 60 MB（gzip 后约 20 MB） | PR #1（`v6/docs/web.md`、`v6/tools/build_web.ps1`） |
| Web 包内容 | 本次用 `strings dist/web/index.pck` 确认：`scenes/editor.tscn.remap`、`scripts/editor.gdc` 已在包内 | Web 构建产物 |

也就是说：**“能不能在浏览器里编辑”不是一个从零开始的问题，缺的是入口、界面和存取。**

### 1.2 现在的缺口

1. 没有 Web 入口：Web 导出固定进 `main.tscn`，`editor.tscn` 虽然打进了包，却没有 URL/参数能进。
2. 没有 Web 存取：编辑器写 `res://data/maps/*.json`，Web 下 `res://` 只读；写 `user://` 能落 IndexedDB，
   但那是浏览器本地草稿，不是仓库里的地图。
3. 编辑手感不足：没有属性面板（不能精确输入坐标/角度）、没有多选/框选、没有重做、没有复制粘贴、
   撤销一次要重建全部 174 个节点。
4. 放置不贴地形：拖动/放置都用 `y = 0` 平面，坡地和岸边会放歪；地形高度图其实已经在了（相机在用）。
5. 只能改变换：改不了单件颜色/自发光、环境光/时段、串灯、水面、粒子、角色参数、道路、区域散布。
6. 手机上没有编辑器 UI：现有编辑器强依赖键盘（Q/E、[ ]、Ctrl+Z/S、Del），触摸只能看不能编。
7. 没有地图管理：只有一张默认图（`campground.json` 与编辑器另存出来的 `campground_edit.json`），
   没有列表、新建、另存、分享链接。
8. 保存没有版本/备份：覆盖写，写坏了只能靠 git。

## 2. 目标与边界

### 2.1 目标

- **一个数据源**：观看器、编辑器、桌面、Web、Android 都读同一份 `map.json`，不出现“编辑器里是这样、发布出去是那样”。
- **两条入口**：桌面 Godot（完整体验）+ 浏览器 `?edit=1`（免安装，能改到 80% 的常用操作）。
- **编辑即预览**：编辑器与观看器共用同一套渲染管线，改完保存，观看器/分享链接立刻看到。
- **不破坏现有成果**：默认外观与页面 viewer 的对齐（mean|diff| = 3.53/255）不能因为加编辑器而漂移；
  v1 地图、现有工具、Android 构建保持可用。

### 2.2 首版不做

- 通用 3D 建模/任意模型导入（只编辑现有 62 类 part 库）。
- 全量地形雕刻/改地形网格（局部抬高/压平作为可选 spike，见 §5.8；全量改地形不做）。
- 实时多人协作、云端版本历史、权限系统。
- 物理碰撞、可走性、寻路（当前项目只有角色游走，没有碰撞需求）。
- SSAO、Glow、屏幕空间反射等 Forward+ 特性（Web 用 Compatibility，观感会不一致）。

### 3.3 不建议承诺的

- **全量地形雕刻/挖山填湖**：terrain 是拆件器烘出来的**一整块网格**（ground 22,540 三角形 / 67,620 顶点，
  triangle soup，另有独立 shadow mesh；water 3,890 三角形），改高度会牵动法线、阴影、水岸与依赖地形的摆件，
  默认不做。**但“局部抬高/压低/压平（±2 m、营地周边）”可以做实时预览**，方案见 §5.8；
  建议先用 2–3 天 spike 验证 Web 上的手感与帧率，再决定是否排进版本。首版仍用“贴地摆放 + 路径带 + 散布”覆盖大部分布局需求。
- **真实水面反射/折射**：Web 是 Compatibility，屏幕空间反射不可用；用程序化波纹 + 假高光即可。
- **任意模型导入/建模**：编辑器只认 part 库里的 174 个变体。
- **多人实时协作**：需要服务端状态、冲突合并、权限，和“单机编辑器”不是一个量级。

## 4. 技术路线选择

| 路线 | 做法 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| **A. 继续用 Godot** | 在 `editor.gd` / `main.gd` 上增量，桌面与 Web 同一套 | 复用已对齐的渲染、part 库、相机/触摸、高度图；`editor.tscn` 已在 Web 包里；一套代码两平台 | Godot Control 的移动端 UI 要专门适配；首屏仍要下 Web 运行时 | **推荐** |
| B. 另做 Three.js 编辑器 | 新的 Web 前端读 `map.json`，自己加载 part | UI 自由、启动快、易做分享/协作 | 要把 174 个 `.tscn` 变体重新导出/加载；重做渲染对齐（现在 1.4% 像素差是花了很多轮才到的）；两套渲染路径会漂移 | 暂不推荐 |
| C. 2D 俯视布局器 + 3D 预览 | 平面拖拽为主，3D 只做预览 | 大范围摆布局快，门槛低 | 做不了高度/材质/灯光/粒子；等于再维护一套数据操作 | 可作为后续补充，不做第一版 |

选 A 的核心理由：**这套工程最贵的东西（和官网 viewer 逐项对齐的渲染、拆好的 174 个 part、相机与触摸、地形高度图）已经在了**，
编辑器缺的是“壳”和“存取”，不是渲染。另起一套等于把这些再付一遍。

## 5. 技术方案

### 5.1 总体结构

```
main.tscn（Web 带 ?edit=1 时切到 editor.tscn）
  └─ WorldView（main.gd：载地图、环境/光、相机、高度图、接触阴影）
       ├─ Viewer                （只读观看）
       └─ Editor（editor.gd）
            ├─ EditorCore       选择 / 命令 / 撤销重做
            ├─ EditorUI         工具栏 / 素材库 / 属性面板 / 状态栏
            ├─ Gizmo            移动/旋转/缩放手柄
            └─ MapIO            res:// / user:// / HTTP / 下载导入
MapWorld（schema v1→v2、读写、part 拼装）
look.json（默认外观） + map.environment（每张地图的覆盖）
```

不在第一版做大重构。`editor.gd` 现在继承 `main.gd`，短期继续用继承；等 UI 变复杂再抽出
`WorldView`，避免为了“架构好看”先引入一轮回归风险。

### 5.2 数据模型 v2（向后兼容）

```json
{
  "version": 2,
  "name": "campground",
  "grid": 4.0,
  "environment": {
    "preset": "day",
    "sun": { "color": "#fff2e0", "energy": 0.7639, "dir": [4, 7, 5] },
    "exposure": 1.0,
    "fog": { "enabled": false }
  },
  "items": [
    {
      "id": "tent-a1",
      "part": "dome-tent",
      "pos": [1.8, 0.0, 9.6],
      "rot_deg": [0, 0, 0],
      "scale": [1, 1, 1],
      "layer": "props",
      "group": "site-a",
      "locked": false,
      "props": { "tint": "#ffffff", "emission": 0.0, "roughness": 0.9 }
    }
  ],
  "effects": [
    { "type": "campfire", "pos": [-2.0, 0.0, 3.5], "params": { "smoke": 0.6, "embers": 0.3 } }
  ],
  "actors": [
    { "part": "park-ranger", "mode": "walk", "wander": 6.0, "path": [] }
  ],
  "paths": [
    { "kind": "boardwalk", "points": [[0, 0, 0], [4, 0, 2], [8, 0, 6]], "spacing": 2.0 }
  ],
  "markers": [
    { "type": "spawn", "pos": [0, 0, 0] }
  ]
}
```

兼容规则：

- 读取 v1 时在内存里补 `version: 2`、`id`、默认 `props`；写入时统一 v2。
- 不认识的新字段原样保留，旧观看器仍能读 `items`，不会因为多了 `effects/actors` 而崩。
- `MapWorld.item_transform` 的数值舍入规则不变；v1 地图不迁移也能继续用。
- `verify_map` 只依赖 `items[]`；`split_parts` 从 GLB 重新拆件，与地图无关。都不受影响。
- 若启用 §5.8 的可选地形编辑，再增加 `terrain` 段（高度图 base64 或 sidecar），默认没有；
  v1/v2 地图不启用时完全不受影响。

### 5.3 编辑器内核

- **命令栈**：`AddItem / RemoveItems / TransformItems / SetProps / Reorder / SetEnvironment`，
  每个命令只动受影响的节点；拖动过程中合并为一条（按下时记录起点，松手时提交）。
  这样撤销不再 `_rebuild()` 重建 174 个节点，Web 上也不会卡。
- **选择**：保留 AABB 射线（对这套大件够用）；多选/框选维护 `selected_ids`；选中框用线框，不给每个选中件复制网格（省 draw call）。
- **Gizmo**：三轴箭头 + 旋转环 + 缩放方块，射线与平面求交；吸附档位与键盘一致；手柄在手机上放大到 48 px 以上。
- **属性面板**：位置/旋转/缩放用可拖动数值框；材质/灯光/环境用分组面板；所有数值改动走命令栈。
- **贴地**：直接用 `main.gd` 已有的 `_ground_at(x, z)`（0.5 m 栅格、双线性采样），
  放置/拖动时把 y 设成地面高度；可选按高度场梯度贴合坡面。岛外/水面回退到 0。
- **存取**：原子写（先写 `.tmp` 再 rename），覆盖前留 `.bak`；`dirty` 状态；每 30 s 自动存 `user://maps/_autosave.json`；
  关闭页面前提示。
- **自检**：把 `--edit-selftest` 扩成覆盖“放置 → 多选移动 → 撤销 → 重做 → 存 → 读 → v2 字段比对”，
  Web 端用 `?edit=1&selftest=1` 跑同一段逻辑并打印 PASS，方便无头验证。

界面（桌面）：

```

│ 地图 campground ▾   新建  另存  导出  保存  分享     ●未保存    │
```

### 5.4 场景效果怎么落地

- **单件材质**：构建时如果 `props` 有覆盖，给这一件复制一份 `StandardMaterial3D`（或 `ShaderMaterial`），
  其它实例继续共享去重后的材质。注意 `_dedupe_materials` 不能再把这份覆盖材质合并掉。
- **环境**：`look.json` 仍是默认值；地图里的 `environment` 只覆盖差异。切换预设时重建
  `WorldEnvironment` + 两盏平行光 + 接触阴影（延迟到拖动结束）。默认 `preset = "day"`，雾关闭，
  保证现有对齐结果不动。
- **串灯**：这套 kit 的串灯没有自发光材质，只有几何体。做法是给灯泡所在的表面换自发光材质
  （颜色/能量；如果整条是一块网格，就整条轻微发光 + 两端各 1–2 盏 `OmniLight3D` 补环境），
  闪烁用很轻的 script；不要逐灯泡加灯（几十盏灯会把 Web 拖垮）。
- **营火/粒子**：`effects` 里存预设名和参数，运行时挂 `GPUParticles3D`（Compatibility 下先实测；
  不稳就退回 `CPUParticles3D`，数量小，观感够用）。萤火虫用低密度、长寿命的 CPU 粒子即可。
- **水面**：terrain part 的 `water` 子网格（`transparency=4`、白色 0.84、roughness 0.5）换成
  `ShaderMaterial`：颜色、透明度、两层程序化波纹、假高光；参数存 `props.water`。默认不换，保持原样。
- **角色**：`ActorSystem` 现在从 `look.actors.per_part` 读全局配置。v2 把每项配置挂到对应 `items[].props.actor`，
  `actors.gd` 优先读物件级配置；巡逻路径存 `actors[].path`，实现“走到点 → 停 → 下一点”。
- **路径/道路**：样条只做数据与手柄；栈道/围栏/木桩按弧长采样，复用现有 part，存 `paths[]`。
  贴地土路用一条窄 ribbon 网格 + 透明材质，沿高度场抬 2 cm，避免 z-fighting；Compatibility 下也能画。
- **散布**：按种子做确定性随机，撒点后逐个查最小间距、查 `_ground_at` 是否在岛上；一次散布 = 一条命令，可整体撤销。

### 5.5 Web 入口、加载与保存（关键）

**入口**：单个 Web 构建，URL 区分：

```
https://dev.wulie.tech/                 观看
https://dev.wulie.tech/?edit=1          编辑器
https://dev.wulie.tech/?edit=1&map=x    编辑指定地图
https://dev.wulie.tech/?map=x           观看指定地图（分享链接）
```

`main.gd` 在 `_ready()` 最前面用 `JavaScriptBridge` 读 `location.search`，命中 `edit=1` 就
`change_scene_to_file("res://scenes/editor.tscn")` 并 return。`editor.tscn` 已经在 Web 包里，
不需要第二个导出预设，也不需要改 `project.godot` 的主场景。

**地图加载顺序**：

1. `GET /maps/<name>.json`（同源 HTTP，`HTTPRequest`）；
2. 失败则回退 `res://data/maps/<name>.json`（PCK 内置）；
3. 再失败给默认地图 + 明确报错。

`build_web.ps1` 把 `v6/data/maps/*.json` 复制到 `dist/web/maps/`。这样**地图数据在 PCK 外**，
改地图不用重新导出 60 MB 包；观看器和编辑器看到的是同一份文件。

**保存**（开发环境，dev 隧道后面有 Authelia）：

```
POST /api/maps/<name>        Content-Type: application/json
→ 校验 name（^[a-z0-9_-]{1,64}$）、大小（< 2 MB）、JSON 结构
→ 写 v6/data/maps/<name>.json 与 dist/web/maps/<name>.json（先 .tmp 再原子替换，旧文件留 .bak）
→ 200 {"ok":true,"bytes":...}
```

`serve_web.py` 增加这个端点即可（约 40 行），不需要数据库。公开部署时只读：
静态托管只发 `dist/web/maps/`，`/api/` 不暴露。

**Web 端兜底**（即使没有保存 API 也能用）：

- “导出 JSON”：`JavaScriptBridge` 生成 Blob 下载；
- “导入 JSON”：隐藏 `<input type=file>`，读文本后交给 Godot；
- `user://maps/_autosave.json`：浏览器 IndexedDB 里的草稿，刷新不丢，但**不作为交付物**；
- 保存失败/离线时明确提示，不假装成功。

### 5.6 手机端

现有观看器的手势已经调好（单指环绕、双指捏合、双指平移），编辑器不能抢这套手势。建议：

- 底部工具栏：选择 / 移动 / 旋转 / 缩放 / 放置 / 撤销 / 重做 / 保存；图标 + 文字，命中区 ≥ 44 px。
- 单指点选；单指拖**已选中的 gizmo** = 编辑；单指拖其它区域 = 环绕；双指永远是相机。
- 长按 = 上下文菜单（复制/删除/替换变体/锁定）。
- 属性面板做成底部抽屉，不再挤在左上角。
- “锁定镜头”开关：放件时避免误转视角。
- 屏幕小的设备默认进观看模式，编辑器作为可选项。

### 5.7 性能预算

- 现状：174 件、约 1074 draw calls；Mali-G925 在 2800×1260 下 60 fps（vsync 锁），瓶颈是 draw call 不是像素。
- 编辑器新增开销：网格、gizmo、选中框、幽灵预览，合计 < 20 draw calls；不要用“复制一份网格做描边”的方案。
- 接触阴影：Web 的 `get_image()` 回读慢；拖动时不重烘，松手/保存时防抖重烘一次。
- 规模建议：≤ 300 件 Web/手机都轻松；300–1000 件需要把重复变体合 `MultiMesh`；> 1000 件要分块/LOD，
  不在首版范围。
- 首屏：Web 仍要下约 60 MB（gzip ~20 MB）；编辑器不额外增加资源。内部工具可接受，公开页面要另做轻量观看器。

### 5.8 地形编辑（可选）：能不能实时、怎么让用户用得懂

先直接回答两个问题：

- **能实时变化吗？** 能，但不能靠每帧重建那块烘焙地形。做法是“高度场 + 位移层”：
  CPU 维护 0.5 m 高度网格（复用/扩展现有 `_ground_at`），GPU 用高度纹理在 ground 的
  `ShaderMaterial` 顶点着色器里偏移 y、用相邻纹素算法线；拖动时只更新纹理，松手时提交一笔。
  ground 是 22,540 三角形（67,620 顶点，triangle soup），不需要整体重建；
  Web 目标拖动 30–60 fps，单次笔刷 < 5 ms（桌面）/ < 12 ms（中端手机），以 spike 实测为准。
  原材质是顶点色 + roughness 0.96 的 `StandardMaterial3D`；换成等价的 `ShaderMaterial`，默认外观不变。
  高度纹理由 WebGL2 的顶点纹理采样（vertex texture fetch）读取，需在 Compatibility 下实测。
  **没有 `terrain` 段的地图继续用原 `StandardMaterial3D`**，确保默认外观与现有基准逐像素一致；
  只有启用地形编辑时才换 shader，出问题可整段回退。
- **会不会太抽象、用户不会用？** 会——如果暴露高度图/噪声参数。交互必须是“直接在地面上画”：
  命名笔刷 + 实时等高线 + 剖面 + 自动贴回道具，不出现“高度场/顶点”这些词。

实现要点：

- 高度纹理按**世界 XZ** 映射（不依赖原网格 UV）；笔刷落点/拖动用高度场射线步进，
  避免在坡上错位。否则“看起来点在坡上、实际落在平地”。
- ground 有独立的 `shadow_mesh`（低模阴影）。位移纹理是否自动作用到阴影 pass 要实测；
  不生效就让 ground 用主 mesh 投影，或把同一位移接到 shadow 通道，否则会出现“地形变了、影子没变”。
- `water` 是独立网格（3,890 三角形）。抬高不进水，压低会被水盖住；水岸用 1–2 m 的衰减带遮接缝；
  位移在岛边衰减到 0，避免裂口。
- CPU 高度网格同步更新后，放置道具/相机/角色立刻用新地面；每次笔刷后检测受影响的“悬空/埋土”道具，
  给出一键贴回。
- 数据：`terrain` 段存高度图（196×196 或 512×512；base64 内嵌约 50–100 KB，也可拆 sidecar PNG）；
  一笔一条撤销；观看器/Android/Web 读同一份。
- 备选（spike 对照组）：直接改原 mesh 顶点 + 重算法线 + 同步 shadow mesh。保留原美术最直接，
  但 triangle soup 的法线/阴影处理更麻烦，实时性不如纹理位移。

交互设计（不抽象）：

| 笔刷 | 用户在屏幕上看到什么 | 行为 |
|---|---|---|
| 抬高 / 压低 | 地面圆环 + 实时鼓包/凹坑 + 等高线 | 拖动改高度，只露半径/强度/衰减三个滑杆 |
| 压平 | “营地平台”预览圈 | 圈内压到点击处的高度 |
| 抹平 | 坡度着色变柔和 | 平滑局部起伏 |
| 做缓坡 | 一条从 A 到 B 的坡线 | 两点间插值出坡 |
| 贴水 | 水面线高亮 | 把岸边降到水面附近 |

通用反馈：等高线（0.25/0.5 m）、坡度着色、原貌半透明叠图、剖面线、松手后“3 件道具悬空”提示 + 一键贴回。

一个具体例子（营地东侧加挡风土坡）：

1. 工具栏点「地形 → 抬高」，地面出现 6 m 圆环，强度 1.2 m。
2. 按住拖动，土坡跟着手鼓起来，等高线由绿变黄；旁边 2 顶帐篷、3 把椅子跟着抬，或松手后一键贴回。
3. 松手 → 一条撤销记录；打开「原貌」叠图对比；不满意 Ctrl+Z 整笔回退。
4. 保存 → `terrain` 高度图写进地图；观看器/Android 共用。

```text
改前：  帐篷 ───────── 平地 ───────── 湖
改后：  帐篷 ───╱▔▔▔╲─── 土坡 ─────── 湖
                    ▲ 6 m 圆环内抬高 1.2 m
```

成本：spike 2–3 人日（位移纹理 + 法线 + 阴影 + Web 帧率）；本体 4–6 人日；交互/贴回/撤销 2–3 人日。
建议先 spike，通过再排期；不通过就保持“贴地摆放 + 路径 + 散布”的首版范围。

## 7. 风险与待决策

| 风险 | 影响 | 应对 |
|---|---|---|
| 地形雕刻期望 | 一旦要“全量改地形”，工期和资产风险都跳一个量级 | 首版只做贴地摆放 + 路径 + 散布；局部抬高/压平先做 2–3 天 spike，全量雕刻单独立项 |
| Web 保存可靠性 | 浏览器配额/隐私模式/IndexedDB 同步时机都可能丢草稿 | 服务端保存为主，导出 JSON 永远可用；写前 `.bak`，失败明确报错 |
| 60 MB 首屏 | 手机上首次打开慢，弱网可能失败 | 内部工具可接受；公开分享另做轻量 viewer，或加 CDN/gzip 缓存 |
| Compatibility 差异 | 编辑器里好看、Web 上偏暗；粒子/水面 shader 可能不支持 | 所有效果以 Web 实机截图验收；粒子上 `CPUParticles3D` 兜底 |
| 触屏编辑手感 | 手势冲突、误操作，可能白做一套 UI | 先桌面为主，手机只做常用操作；M2 就上真机验证 |
| 撤销重建全部节点 | Web 上撤销卡顿、内存抖动 | M2 换成命令栈，只改受影响节点 |
| 地图规模 | 超过 300 件后 draw call 和内存吃紧 | 先限规模；后续 `MultiMesh`/分块 |
| 保存接口安全 | dev 隧道后是 Authelia，但仍是写接口 | 名字白名单、大小限制、只写 `data/maps/`、公开部署不暴露 `/api/` |
| 与 PR #1 的依赖 | Web 构建未合入时 M1 无法验收 | M1 等到 PR #1 合入后再做；文档/桌面部分不受影响 |

需要拍板的事（按重要性）：

1. **主战场**：桌面为主、浏览器为辅，还是必须手机可编辑？（决定 M2 的 UI 预算）
2. **地形**：首版接受“只贴地摆放 + 路径/散布”，还是先做 2–3 天 spike 验证局部抬高/压平？（决定是否作为 M4 之后的可选增量；全量雕刻仍不建议）
3. **保存位置**：接受在 dev 环境直接写项目 `data/maps/`（需加保存端点），还是只导出 JSON 手动提交？
4. **分享范围**：只在 Authelia 后面自己用，还是要公开链接给外部看？（决定是否另做轻量 viewer）

我的建议：1 选“桌面为主 + 浏览器可编辑常用操作”，2 选“首版先不做全量雕刻；如果在意挡风/台地，先做 2–3 天 spike”，3 选“dev 保存端点 + 导出兜底”，4 选“先内部，公开另做”。
