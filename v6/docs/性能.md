# v6 性能实测（2026-11-08）

同一天、同一份代码、同一套配置。手机 = vivo V2458A（天玑 9400 / **Mali-G925-Immortalis MC12**，
Vulkan 1.3，面板 1260×2800，当前 90/60 Hz 模式）；桌面 = GTX 1050 Ti。

## 数字

|---|---|---|---|---|---|---|
| 手机 | 2800×1260（原生全屏） | **16.6 ms** | 60 | **1074** | 164.6 MB | 60 Hz vsync 锁死，看不出余量 |
| 手机 | 1400×630（`wm size` 降到 1/4 像素） | **8.38 ms** | 119 | 1074 | 79.4 MB | 像素去掉后露出的**下限** |
| 桌面 | 1246×956 | 5.88 ms | 170 | 1078 | 221.6 MB | 基准视角 |
| 桌面 | 2800×1260 | 9.51 ms | 105 | 1078 | 431.4 MB | 同像素量、不同 GPU |

## 判读

1. **瓶颈是 draw call，不是像素、也不是人物/阴影。**
   手机把分辨率降到 1/4 之后仍然要 8.38 ms，而 draw calls 一个都没少（1074）——说明
   8.4 ms 是 CPU 侧提交 1074 个 draw 的成本；像素那部分在全分辨率下大概再叠 8 ms 左右。
2. 桌面同理：1078 个 draw 在 1050 Ti 上就是 5.9 ms 的底。
3. 1074 个 draw 的来源很直接：174 个 part 各自一套网格（拆件时每件都带自己的 mesh），
   场景里没有做任何合批。人物（4 个 31 骨蒙皮）和接触阴影都是毫秒级零头。
4. 手机上 60 fps 是 vsync 锁的，不能当“跑满”的证据；把 vsync 关掉的构建仍是 60.0 fps，
   说明 Android 侧主循环跟着 60 Hz 走，只有降分辨率到 1/4 时循环才跑到 119 fps —— 那才是
   GPU/CPU 的真实余量口径。

## 如果要提速，按性价比排

1. **静态合批**（最大头）：按区域把 part 的网格合并成少数几个多网格，
   draw 1074 → 几十，预计手机帧时能从 16.6 ms 降到 9~11 ms、桌面 5.9 → 2~3 ms。
   v3 里有现成的 `static_merge.gd` 可以搬。
2. **降渲染分辨率**：手机 2800×1260 是 3.5 MPx，按 0.8 缩放到 2240×1008 大约省 1.5~2 ms，
   代价是轻微发软。
3. 阴影 2048 已经比桌面的 4096 低一档；再降到 1024 省的是阴影 pass 的 draw（1074 里约一半）。

> 注：以上都是「看效果优先」阶段记录的数字，没有为性能改过观感。

## 怎么读这张表

1. **v6 比 v3 快 2.3 倍，便宜的全部来源只有一个：draw call 少一半**（1078 vs 2651）。
   两边「每 draw 的成本」几乎一样：v6 4.8 µs/draw、v3 4.4 µs/draw。
2. **三角面在这个量级不贵**：v6 只有 16 万面，v3 是 162 万面，但帧时只差 2.3 倍而不是 10 倍
   —— 面数被 draw call 的成本盖住了。
3. **v3 合批反而更慢**（11.78 → 12.0~12.1 ms）：draw 从 2651 降到 1648，但三角面从 162 万涨到
   246 万（合并丢剔除），两头相抵。说明 v3 是「draw + 面 + 填充」一起贵，和 v6 的纯 draw 瓶颈不同。
4. **hd3d-ref 是反面例子**：2857 draw + 2 GB 显存（逐栋贴图），帧时是 v6 的 3.7 倍。
5. v4 的 2.5D 精灵版便宜到没有比较意义（不到 1 ms），但它是 2D 观感，不在同一目标上。
